API, Kesako?

Prerequisites: HTTP Request

HTTP is the protocol the web talks over: a client sends a request, a server sends back a response, and the exchange ends there — every call is a fresh one, and nothing is remembered in between.

CRUD & the request/response format

Four operations cover nearly everything you will ever do to a resource — create it, read it, update it, delete it. HTTP gives each one a verb.

  • GET Read — fetch a resource, change nothing
  • POST Create — add a new resource
  • PUT Update — replace an existing resource
  • DELETE Delete — remove a resource

Status codes

Category Range Meaning Examples
Informational 1xx Hold on - received, still working 100 Continue
Success 2xx Here you go - it worked 200 OK · 201 Created
Redirection 3xx Look elsewhere - moved, or already cached 301 Moved · 304 Not Modified
Client error 4xx Your fault - malformed or not allowed 400 Bad Request · 404 Not Found
Server error 5xx Their fault - the server broke 500 Internal Error · 503 Unavailable

TCP/IP is the four-layer stack every internet exchange rides on. It cuts a message into packets, routes them across whatever networks sit in between, and puts them back in order at the far end. HTTP lives on the top layer and simply trusts the layers below to deliver — which is why an API call never has to think about cables, Wi-Fi or undersea fibre.

API Styles

A web API is an API you reach over HTTP: one program calls another across the network, using the request/response exchange we just saw. That leaves a lot open — how a call is addressed, who decides what comes back, how the two sides agree on the shape of the data. A style is the set of conventions a team picks to answer those questions. Three of them cover almost everything you will meet.

The default for public web APIs. Everything is a resource with its own address, and the familiar HTTP verbs act on it — readable straight from the URL, easy to cache, easy to explain. Six principles hold it together:

  1. Client–server The side that asks and the side that answers stay separate. Either can be rebuilt without touching the other.
  2. Stateless Every request carries everything needed to answer it. The server remembers nothing between two calls.
  3. Cacheable A response says whether it may be kept and reused, so the same question need not be asked twice.
  4. Uniform interface One predictable way of naming and addressing things — learn one endpoint and you can guess the next.
  5. Layered system Caches, gateways and load balancers may sit in the middle. The caller cannot tell, and does not need to.
  6. Code on demand (optional) The server may send a snippet of code for the client to run. Rarely used in practice.

One single address, and the caller writes the shopping list.

With REST the server decides what a response contains; with GraphQL the client asks for exactly the fields it wants and gets back exactly those — no more, no less. That removes the two classic frustrations: receiving a fat object when all you needed was a name, and having to make three round trips to fill one screen.

The price is paid elsewhere. Because every request is different, the easy wins of REST — caching a response, capping how much a caller may ask for — become real work. It shines when many different screens need many different slices of the same data.

Built for machines talking to machines, fast. Rather than human-readable text, gRPC sends a compact binary format down a connection that stays open, and both sides agree in advance on the exact shape of every message. That agreement is written in a .proto file — a contract both programs are generated from, so neither can drift.

Excellent between services inside one company; awkward to call straight from a browser. Internal plumbing rather than public front door. 

syntax = "proto3";

service Catalog {
  rpc GetProduct (ProductRequest) returns (Product);
}

message ProductRequest { int32 id = 1; }

message Product {
  int32  id    = 1;
  string name  = 2;
  double price = 3;
}

What about security ?

Context

  • An API is a door onto your data, and its address is public. Anyone who knows the URL can knock.
  • Nothing in an HTTP call proves who sent it — the request we just built would run exactly the same from any laptop on earth.
  • So before an API answers your question, it answers two of its own.

Stakes

  • The data. One unguarded endpoint can hand over the whole customer table in a single call.
  • The bill. Calls are metered, and one key names the payer. A leaked key spends someone else’s budget, and the someone else is you.
  • The trust. A breach stops being a technical problem and becomes a legal one.

Methods and Framework

1/2

The previous slide asked two questions. Each one has its own toolbox — and both toolboxes ship their answer in the same place: an HTTP header.

Authentication

Two ways to prove who is calling. Both are just a string in a header. What differs is whether the string means anything and how long it lives.

API Key

A long random string the provider hands you once. The server keeps its own copy and compares the two. 

X-API-Key: 3f9a1c7e-84d2-4b6a-9e2f-7c1a5d9b0e42
  • Carries nothing. The string says nothing on its own — the server has to look it up to learn who you are.
  • Never expires until somebody revokes it, which is exactly why a leaked key stays useful for years.

JWT — JSON Web Token

Three chunks separated by dots: header, payload, signature. The payload is readable by anyone; the signature is what proves the server issued it. 

Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJlZGl0b3IifQ.Kx8h…
payload, decoded — no secret needed
{ "sub": "42", "role": "editor", "exp": 1789243200 }
  • Carries its claims. Who you are, what role you hold, when it dies — all in the token, so no lookup.
  • Expires on its own, often within the hour. A stolen token has a short life.

Methods and Framework

2/2

Authorization

The API now knows who you are and decides what you may touch. RBAC is the model that answers it; OAuth is how the token carrying that answer gets issued.

RBAC — Role-Based Access Control

Permissions are never granted to people. They are granted to roles, and people are handed a role — so a new joiner is one assignment, not twenty.

  • viewer GET — may read the cart
  • editor GET, POST, PATCH — may add and change items
  • admin everything, DELETE included

The JWT on the previous page says "role": "editor". So a DELETE comes back 403, not 401 — authenticated, simply not authorized.

OAuth 2.0 — the valet key

The one everybody has already used: every “Sign in with Google” button is OAuth. Its job is delegation — letting an app act for you without ever seeing your password.

  • The app sends you to the provider. You log in there — never inside the app.
  • You approve a scope: calendar.read, not “my whole account”.
  • The app gets a short-lived token — usually a JWT — and calls the API with it. Revoke it any time, without changing your password.

And for performance ?

Context

  • One call is cheap. A thousand a second is not — and nothing in the request tells the server apart an eager client from a broken one.
  • So scale is answered at two levels: the contract fixes what a caller is allowed to ask for, and the infrastructure absorbs what is actually asked.

Rate limiting

A ceiling on how many calls one caller may make per window. The API answers, and tells you where you stand. 

X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
Retry-After: 37
  • Every response carries your remaining budget, so a well-written client slows itself down before it gets stopped.
  • Cross the line and it is 429 Too Many Requests — a refusal, not a failure. Wait Retry-After seconds and the same call works.

Pagination

A ceiling on how much one call may return. The collection comes back in slices, and the response says how to walk them. 

GET /products?limit=20&skip=40

{ "products": [ …20 items… ],
  "total": 194, "skip": 40, "limit": 20 }
  • total is the whole collection; limit and skip are your window onto it. Page 3 is simply skip = 2 × limit.
  • Never assume the first page is the answer. Reading 20 rows while total says 194 is the most common bug in a first integration.

Infrastructure Best Practices

The previous slide was the contract level — what a caller is allowed to ask for. This is the other one: what stands behind the API so that the calls it does allow stay fast, whatever the load.

  1. Caching
  2. Load balancing

Caching

Answer it once, then keep the answer — the fastest call is the one that never has to reach the server.

Load balancing

One address in front, several servers behind it — the traffic is spread before any single machine feels all of it.
